# Decisions

Each entry: decision · reason · main alternative rejected. These feed the README's trade-offs section.

| # | Decision | Reason | Main alternative rejected |
|---|---|---|---|
| D1 | One Next.js app (App Router, TypeScript strict) on Vercel; API routes are the Node backend | One deploy, one type system shared by UI and backend, no CORS; fits a 12-hour budget | Separate FastAPI backend + Next.js frontend (two deploys, duplicated types) |
| D2 | Modules `lib/agent`, `lib/tools`, `lib/rag`, `lib/guardrails`, `lib/voice`, `lib/observability`, `lib/session`, `lib/db`; shared types in `lib/types.ts`; UI in `app/` + `components/` | Clear boundaries between UI, orchestrator, tools and vector store, which the rubric grades directly | Feature-folder layout mixing UI and backend code per feature |
| D3 | Neon Postgres + pgvector for sessions, messages, traces and embeddings | One managed store for relational state and vectors; serverless driver works on Vercel; joins between chunks and metadata (tier) are plain SQL | Pinecone/Qdrant for vectors + separate DB for state (two services, two consistency stories) |
| D4 | Custom typed state machine for the agent loop | Every state and transition is explicit, typed and testable; easy to emit step events and to force an escalation state | LangGraph/Mastra (more abstraction to learn and debug inside the time budget) |
| D5 | SSE for chat with typed events `step_started`, `step_completed`, `token`, `error`, `trace`, `done` | One-way server→client stream is all chat needs; works over plain HTTP on Vercel serverless | WebSockets (need a stateful server, not supported by Vercel functions) |
| D6 | Voice via OpenAI Realtime API over WebRTC; backend issues ephemeral tokens | Lowest-latency speech-to-speech with built-in VAD and barge-in; browser never sees the real API key | STT → LLM → TTS pipeline (higher latency, interruption handling built by hand) |
| D7 | Voice tool calls go to the same backend tool/guardrail endpoint as chat; voice transcripts saved into the same session | One policy and guardrail path for both modes; consistent multi-turn memory across modes | Defining tools client-side for voice (duplicate logic, policy bypass risk) |
| D8 | Guardrail = similarity threshold calibrated on a labeled eval set + grounding check (answer must cite retrieved chunks); low confidence → escalation state | Threshold is measured, not guessed; citation check catches answers not backed by retrieved text | Prompt-only "say I don't know if unsure" (not measurable, not enforceable) |
| D9 | Policy (refund limits, tier, identity, contract status) enforced in tool code; refund tool idempotent | The LLM cannot talk its way past a rule; retries never double-refund | Policy rules in the system prompt only |
| D10 | Retrieved documents are wrapped and treated as data, never as instructions | Prevents prompt injection through the knowledge base | Trusting corpus text inline in the system prompt |
| D11 | Raw SQL migrations in `db/migrations/*.sql` applied by a small Node script using `@neondatabase/serverless` | No ORM to learn or configure; schema is readable; pgvector types need raw SQL anyway | Drizzle/Prisma (extra setup and codegen, weak pgvector support) |
| D12 | Embedding size 1536 (`text-embedding-3-small`) | Cheap, good quality, same provider as Realtime so one API key | `text-embedding-3-large` (3072 dims, higher cost, marginal gain on a small corpus) |
| D13 | Section-aware chunking: one chunk per `##`/`###` section, labelled with its heading path; cap 350 tokens, 40-token overlap only when a section is split | Policy rules are bounded by sections (a tier's limit, window and conditions sit together). Fixed windows cut a limit off from its conditions and mix tiers in one chunk, which breaks tier filtering and makes citations vague. Corpus sections are 19–188 tokens (median 66), so a 350 cap (about 2× the largest) keeps every section whole; the cap and overlap only matter for future long sections | Fixed 512-token windows with overlap |
| D14 | Tier scope stored per chunk (front matter, narrowed by `<!-- tiers: … -->` per section) and filtered in SQL, with `hnsw.iterative_scan = strict_order` | The filter is enforced in the query, not by the model; iterative scan keeps returning k rows when the filter is narrow | Filtering after retrieval in app code (can return fewer than k), or one index per tier |
| D15 | Models pinned in `lib/config.ts`: answers `gpt-5.4-mini` (reasoning off), grounding check `gpt-5.4-nano` | Checker picked by a hand-labelled sanity set (evals/RESULTS.md): `gpt-5-nano` is cheapest ($0.05/$0.40 per 1M tokens) but scored 6/8, then 7/9; `gpt-5.4-nano` scored 8/8, then 9/9, at about $0.0002 per check and ~1 s | `gpt-5-nano` (cheaper, but passed an answer with an added false claim) |
| D16 | Two-gate guardrail: top-1 similarity ≥ 0.28, then a grounding gate (answer declined, missing or invalid citation, or unsupported claim → escalate). Threshold from a stated rule on the calibration split | Similarity alone can't separate near-miss questions (0.32–0.58) from answerable ones (0.34–0.75); getting it to 0 missed needs t ≥ 0.58, which escalates 67% of answerable queries. The threshold screens clear out-of-scope queries (0.10–0.30) before any LLM call; the grounding gate catches near-misses | Retrieval-only threshold at 0.58 |
| D17 | Injection defence in layers: ingest-time pattern scan quarantines a chunk (stored, excluded from retrieval); retrieved text escaped and framed as data; the claim checker rejects claims that rely on instructions; policy enforced in tool code (phase 3) | No single layer is trusted: the quarantine guarantees the injected text never affects scores or citations, and the other layers cover patterns the scan misses | Dropping whole documents (loses their legitimate sections), or prompt-only defence |
| D18 | Token counts approximated as characters / 4 | Only used for chunk sizing, where ±10% doesn't matter; avoids a tokenizer dependency | `tiktoken` |
| D19 | Eval split (20 calibration / 10 held-out) fixed in `evals/guardrail_set.jsonl` before any scoring; the sweep uses calibration rows only; held-out is scored only at the chosen threshold | Keeps the held-out rates an honest estimate | Picking the threshold on all 30 queries |
| D20 | Injection detector: 9 generic regex categories (override instructions, text addressed to an AI/bot/agent, forced approval, "do not escalate", "from now on" overrides, skip/bypass checks, encoded payloads) run on every chunk of every document at ingest; a match quarantines that chunk only. The detector version is part of the ingest hash, so changing a pattern re-scans everything | Generic, cheap and deterministic; nothing refers to a specific document. Corpus: flags only `partner-program-faq#2`, no false positives. Probe set (which also guided the patterns, so not an independent measure): 4/6 paraphrased attacks caught, 0/3 benign policy lines flagged. **Limits:** misses other languages, synonyms outside the patterns, and false "policy" written as ordinary policy text (e.g. "the refund limit is now unlimited"). Those are covered by the later layers: the claim checker only accepts claims stated in cited text, and refund limits are enforced in tool code | An LLM classifier at ingest (better recall, but non-deterministic and itself injectable), or no ingest-time filter |
| D21 | Rate limits as fixed-window counters in Postgres: `/api/rag/search?answer=1` 10 per IP per 10 min + 200 per day globally; chat 30 per IP per 10 min + 600 per day. IPs are hashed before storage. Fails closed (503) if the counter can't be written | Serverless instances share no memory, and Neon is already there (no new paid service). The global daily cap bounds OpenAI spend even if many IPs are used | Upstash/Redis (another service), in-memory per-instance limits (ineffective on serverless) |
| D22 | Agent model `gpt-5.4-mini` (reasoning off, one tool call per step, `parallel_tool_calls: false`) | Live scenarios (evals/AGENT_RESULTS.md): `gpt-5.4-nano` went 3/6, then 5/6 after required escalations moved into code, but its remaining failure is an action nobody asked for (it opened a ticket instead of attempting the refund). `gpt-5.4-mini` went 5/6; its one miss was asking again for the email instead of reusing it (safe). nano costs about a third as much ($0.008 vs $0.026 for 6 conversations); safety wins | `gpt-5.4-nano` (cheaper, but takes unrequested actions) |
| D23 | Custom typed state machine (`awaiting_input → planning ⇄ executing_tool → checking_claims → responding → completed/escalated`, any → failed); illegal transitions throw; every transition is a trace mark; max 6 tool calls per turn, then `tool_choice: none` | Explicit and testable; the step cap stops tool loops | LangGraph (more machinery than four tools need) |
| D24 | Policy in tool code: identity before any account tool; refund checks contract status → invoice → chargeback → already refunded → amount → window → tier limit. Escalations that policy *requires* (billing error after contract end, suspension, chargeback, 3 failed verifications) are opened by the tool itself; offered ones (over limit, out of window) only on the customer's request | The model can ask for anything, and the code decides. Moving required escalations into code took nano from 3/6 to 5/6 and removed a source of variance | Asking the model to escalate (it skipped or over-did it in live runs) |
| D25 | Refund tool is write-ahead and idempotent: `begin` (pending row, unique idempotency key = sha256(session, invoice, amount)) → policy check → `complete` (succeeded/rejected) → only then acknowledge. A replay returns the stored result; a ledger write failure returns TOOL_FAILURE, never success. Already-refunded checks read the CRM and the ledger, so another session can't refund the same invoice twice | Never acknowledge what isn't recorded; retries are safe | Acknowledge then log (can claim refunds that were never recorded) |
| D26 | Claim gate: the reply streams through a sentence buffer; each sentence that claims a refund or ticket (or names a ticket id or refunded amount) is checked against this turn's tool results and replaced with the truth if it doesn't match | Real streaming with a sentence of delay, and no false action claims reach the customer | Checking only after the full reply (no streaming), or trusting the prompt |
| D27 | Session log: append-only `session_events` (DB trigger blocks UPDATE/DELETE), `seq` numbered per session; agent context and verified identity are rebuilt from it each turn; the PIN is redacted from logged tool arguments; tool results sent to the model contain tier, contract status and invoices only (no name, email or PIN) | One source of truth that voice can share; audit trail; data minimisation | Keeping state in memory per request (lost between serverless invocations) |
| D28 | Prompt layout: fixed system prompt + fixed tool definitions first, then the conversation | Stable prefix for OpenAI prompt caching (cached tokens are recorded in the trace) | Injecting per-turn state into the system prompt (breaks the cache) |
| D29 | Voice model `gpt-realtime-2.1-mini` over WebRTC; transcription `gpt-4o-mini-transcribe`; voice `marin` | Speech-to-speech with built-in VAD and barge-in. The mini costs $10/$20 per 1M audio tokens vs $32/$64 for `gpt-realtime-2.1`, and quality was fine for short support answers in the live checks. A 3-minute session of testing cost about $0.06 | `gpt-realtime-2.1` (3.2x cost); OpenAI's newer GPT-Live product (different API, outside the decided design) |
| D30 | Ephemeral key from `POST /v1/realtime/client_secrets` (60 s TTL), minted per voice session by `/api/voice/session` (6 per IP per 10 min, 60 per day); the browser does the SDP exchange with that key | The standard key never reaches the browser; the short TTL limits a leaked key to one connection setup | Relaying audio through our own server over WebSocket (not possible on Vercel functions, adds latency) |
| D31 | Voice tool calls go browser → `/api/voice/tool` → the same `runToolStep` as chat (validation, identity from the session log, policy, ledger, logging, step events). Results return as `function_call_output` + `response.create`. Calls from an interrupted/cancelled response are dropped | One policy path for both channels; nothing to trust in the browser; tests assert identical outcomes for the same inputs | Tool logic in the browser, or a separate voice agent |
| D32 | Semantic VAD (eagerness medium) with `interrupt_response: true` | Server VAD with 500 ms silence cut callers off at every pause while reading out an email or PIN (seen live). Semantic VAD waits for the end of the thought and still barges in | Server VAD with a longer silence window (slower turn ends everywhere) |
| D33 | Interruption: on `speech_started` while a response is *playing* (tracked by `output_audio_buffer.started/stopped`, since playback outlasts `response.done`), mute local playback at once, send `output_audio_buffer.clear`, and rely on the server's barge-in truncation (`conversation.item.truncated`), falling back to our own `conversation.item.truncate` with the estimated heard time after 700 ms. The transcript keeps only the heard part (≈15 chars/s, using the server's `audio_end_ms` when it arrives) and is marked "interrupted" | The caller stops hearing the agent as soon as speech is detected (0 ms after the event, about 0.63 s after speech onset, mostly VAD); history and transcript match what was heard | Waiting for the server to stop audio; logging the full generated text |
| D34 | Shared session for voice: the token endpoint replays the last 12 chat/voice messages as conversation items and puts the verified account (tier, contract, invoices; no PII) into the instructions; voice transcripts, tool events and escalations are appended to the same `session_events`; answers still playing at teardown are logged as the heard part | Verify in chat and continue by voice (or the reverse); one transcript; the tool bridge reads identity from the log, not from the browser | A separate voice transcript store |
| D35 | **Known limitation:** the claim check can't rewrite audio already spoken. Mitigation: tool results are authoritative (the refund tool decides), the voice instructions forbid claiming actions not returned by a tool, and each spoken answer is claim-checked when logged; a mismatch is stored on the session event and shown under the message ("Spoken claim not backed by a tool result") | Honest about the gap; the record and the UI still show the truth | Delaying audio until text is checked (adds seconds of latency and defeats real-time voice) |
| D36 | Voice cost controls: 3-minute cap per session enforced by the client (visible timer), per-IP and daily caps on minting sessions and on tool calls; realtime usage from `response.done` is written to `traces` with an estimated cost | Bounds spend on a public demo; usage is visible for the observability drawer | A server-side session watchdog (the server can't close a WebRTC session it isn't part of) |
| D37 | Failure simulation injects real faults at the real boundary (1 ms SDK timeout, a fetch returning a genuine HTTP 429 with Retry-After, refund throwing after the ledger write, embeddings to an unreachable host, client-side stream abort), scoped to one request with AsyncLocalStorage and chosen by the visitor per turn | The real handling code runs (SDK error classes, retries, typed errors, ledger recovery), so the demo can't pass on fake UI states | Mocking errors in the UI, or env-var switches that affect every visitor |
| D38 | Agent model retries in our loop (3 attempts, exponential backoff with equal jitter, base 400 ms, cap 4 s, Retry-After wins), SDK retries off for that client; never retried once text has streamed; tools are never retried automatically, but writes are idempotent so a retry by the model or the user is safe. Answer/grounding/embedding calls keep the SDK's built-in retries | Retries become visible (`retrying` events → "busy, retrying…") and can't duplicate streamed text or actions | SDK-only retries (invisible to the user), or retrying whole turns (could repeat tool calls) |
| D39 | A distinct typed error and UI state per failure: `llm_timeout`, `llm_rate_limited`, `llm_unavailable`, `tool_failed` (refund-specific copy and "Try the refund again"), `retrieval_unavailable`, `rate_limited`; fallback replies only state what the turn actually did | Users can tell "busy" from "broken" from "nothing was refunded"; actions match the failure | One generic "something went wrong" |
| D40 | Traces persisted per span (redacted at write time: secrets, masked emails, PINs) with parent ids, cached tokens and channel; chat writes the turn's trace before `done`, voice writes tool traces and realtime usage per response; the drawer reads `/api/sessions/:id/traces` and computes p50/p95 | The drawer works for past turns, reloads and voice; nothing sensitive is stored in traces | Showing only the live SSE `trace` events (lost on reload, no voice) |
| D41 | Costs labelled "estimated": provider-reported tokens (incl. cached) × the pricing table in `lib/config.ts`, with the check date and source shown in the drawer | Honest about what the number is | Presenting estimates as billed cost |
| D42 | Stream resume: every numbered SSE event is also written (batched) to `stream_events`; `GET /api/chat/stream?streamId&after=N` replays and follows; the client de-duplicates by seq; the turn is kept alive with `after()` | Serverless instances share no memory, so the replay buffer must be shared; a client drop doesn't lose the turn | In-memory buffer (a reconnect may hit another instance) |
| D43 | Hardening: zod schemas on every route with a 2,000-char message cap; one typed error body `{error, message, requestId}` with `x-request-id`; JSON structured logs with request/session ids and stacks server-side only; CSP + nosniff + frame DENY + referrer + permissions + HSTS; React error boundaries (`app/error.tsx`, `app/global-error.tsx`); `/api/health` checks DB, embeddings and LLM (model-metadata calls, no tokens) | Production basics, cheap to keep | A WAF / external logging service (outside the free-tier rule) |
| D44 | Voice session length: the Realtime API exposes no session-duration setting, so the 3-minute cap stays client-enforced, backed server-side by `max_output_tokens` (1,500 per response), the 60 s ephemeral-key TTL (connection setup only) and per-IP/daily session caps | Documents the limitation and bounds cost anyway | A server-side watchdog (the server is not part of the WebRTC session and can't end it) |
